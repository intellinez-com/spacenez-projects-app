Automatic client daily status — 2026-11-20

Workflow
- The client's project list shows the latest recorded project action.
- Projects open on Daily status. Today, This week and So far filter actual activity
  by occurrence time. The calendar is Asia/Kolkata; weeks start on Monday.
- Admins and assigned partners use the normal project controls. Changing a task's
  status, dates, title, description, stage, priority or owner creates an event.
  Project stage/status/date/detail edits, file sharing/removal, comments and actual
  approval requests/decisions also appear automatically.
- Entries show who acted, when, the affected task/file, and relevant before/after
  values. Comments and approval feedback are labelled separately from task progress.
- No daily report needs to be posted. Optional notes/questions use Discussion.
  Previously published daily reports are preserved as labelled project notes.
- A day with no recorded activity does not mean no work happened outside the portal.
- Overall progress and open task dates remain the current task snapshot. A task
  marked complete in an event is a recorded status action, not proof of physical work.
- Existing private documents are opened through signed links. Removed files remain
  named in history but do not get an open-file action.
- The timeline and project data refresh every minute while active. Successful app
  mutations invalidate activity immediately; Project Refresh checks it too.

History and access
- public.project_activity is written only by trusted database triggers. Authenticated
  users and the service API cannot directly insert, modify or delete event rows.
- The trigger uses auth.uid() and server time for new events. SQL/service operations
  without an authenticated actor remain unattributed system events.
- Viewer RLS uses can_view_project. Client/partner/admin access remains governed by
  the existing project policies. A visible event's actor can be shown to that reader.
- No-op edits and task revision changes caused only by files create no extra task
  events. Source failures/transaction rollbacks also roll back their events.
- Detailed task-change tracking begins at project_activity_tracking.started_at.
  Earlier task status transitions cannot be reconstructed from current status or
  updated_at. The screen displays the tracking start date/time.
- Historical backfill includes existing file uploads, comments, approval requests/
  decisions and preserved notes using their stored timestamps and known actors.
  These entries are labelled Earlier record. No past task completion was invented.
- The isolated local preview contains fictional activity only; no sample activity
  was seeded into real client projects.
